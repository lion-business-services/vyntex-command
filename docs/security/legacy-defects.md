# Legacy defects, and how this platform prevents each one

The owner's brief, section 88, lists weaknesses of the older internal system (NOVA) that must not be carried over. This page takes each one, says what was wrong, what prevents it here, and which file or test proves it. Where there is no test yet, it says **not yet proven**. Nothing is marked as proven because a feature merely exists.

How to read the evidence column: a path in backticks is a file in this repository, and `test: "..."` is the name of a check inside the file named on the same line. `scripts/security/check-evidence.mjs` verifies that every file and every test named here exists, and runs on every pull request, so this page cannot quietly go stale.

**State on 3 October 2026.** The database tests below pass locally: `bash supabase/tests/run_local.sh` ended with 2,615 assertions passed. They run against local stand-ins for what Supabase provides; nothing here has been verified on a real Supabase project, because none exists yet. The modules for appointments, credits, the service catalog, reviews, access requests and the tax ID request and approval flow were not in the database when this was written; their rows say so.

## The fifteen named defects

| # | Defect in the older system | What prevents it here | Evidence | State |
| --- | --- | --- | --- | --- |
| 1 | **Database functions that run without a sign-in.** All 40 functions could be called with the public browser key. | The anonymous role can execute no function in `public` or `app`. Functions created later are not open by default (a database-wide default set in the first migration). A check at the end of the migrations refuses to finish if any function is open to the anonymous role. | `supabase/tests/rls_isolation.sql` test: "anon cannot execute any function in public or app". `supabase/migrations/0019_lockdown_check.sql`, `supabase/migrations/0029_server_lockdown.sql`. | Proven locally |
| 2 | **Client names readable by anyone.** A function returned the name and office of every client to any caller, signed in or not. | A visitor who is not signed in reads nothing at all. Inside a company, a client that belongs to an office is hidden from people of other offices, together with everything attached to it. By the owner's office rule, a signed-in member of the same company still gets the name and office of a hidden client so that they can ask for access; nobody outside the company does. | `supabase/tests/rls_isolation.sql` test: "anon holds no privilege on any table or view in public". `supabase/tests/gateway.sql` test: "staff of the first office see its client and not the client of the second office" and test: "a hidden client cannot be edited". | Proven locally for the public case and the office scope. The access request and approval tables: **not yet proven** (not built). |
| 3 | **Anyone could sign up and become staff.** | There is no sign-up route. An account exists only through an invitation created by a member who holds the capability, or the one-time invitation of a company's first owner. Sign-up is also switched off in the sign-in service (a setting, `docs/DEPLOYMENT.md` section 4). | `tests/server/auth.e2e.test.mjs` test: "no sign-up: every way in refuses an account that was not invited, and says nothing about which accounts exist". `supabase/migrations/0022_invitations.sql`. | Proven against the local stand-in. The setting: requires configuration. |
| 4 | **Sensitive files in a public bucket**, with uploads of any size and type. | Buckets are private. Files are stored under the company with a server-made name, read back through a link that lasts one minute and belongs to one person, and limited in size and type. | `supabase/tests/rls_isolation.sql` test: "the worker documents bucket is private". `tests/server/ws.e2e.test.mjs` test: "files: nobody uploads into, or reads from, another company" and test: "files: size and type limits, and the content must be what the type says". | Proven against stand-ins. The real Storage service was not exercised. |
| 5 | **Broad write permissions.** One rule let every signed-in account change whole tables. | Every write rule asks for the general "write" capability and for the capability of that kind of record, per company, and the same matrix is compared between the app code and the database. | `supabase/migrations/0013_access_rules_v2.sql`. `supabase/tests/gateway.sql` test: "the owner holds every capability in every edition". `supabase/tests/parity.mjs`. | Proven locally |
| 6 | **The read-only role could change prices.** | The read-only role holds no "write" capability, so it changes nothing, in any table. | `supabase/tests/rls_isolation.sql` test: "after every attempt by the read-only person the company data is byte for byte unchanged". `tests/server/ws.e2e.test.mjs` test: "a read-only member can load, and their changes are rejected by the gateway". | Proven locally for every table that exists. The service catalog and its prices: **not yet proven** (table not built). |
| 7 | **A payment action could be repeated and minted a credit each time.** | Changes carry an idempotency key: the same key returns the first answer and changes nothing again. Server actions have the same protection. | `supabase/tests/gateway.sql` test: "a payment sent twice with one key (a double click, a retry) is recorded once". `supabase/migrations/0024_idempotency.sql`. `tests/server/ws.e2e.test.mjs` test: "apply is safe to repeat: the same key gives the first answer and changes nothing again". | Idempotency: proven locally. Appointment payment and credits: **not yet proven** (not built). |
| 8 | **Staff could repoint a client at another client's stored tax ID.** The pointer was an ordinary editable column. | There is no pointer. The tax ID lives in its own table that no role can read or write directly. The type and last four digits shown on the client are copied from it by the database and cannot be set by anyone, the server key included. | `supabase/tests/gateway.sql` test: "client_secrets has no policy at all", test: "the owner cannot change the last four digits" and test: "nor create a client that looks as if a tax ID were on file". | Proven locally |
| 9 | **A senior could approve their own request to see a tax ID.** | Planned: request, decision by a different person, one-time reveal, each step recorded. What exists today: a fresh identity check is required for protected operations, and every read of a worker tax ID is recorded. | `tests/server/auth.e2e.test.mjs` test: "fresh identity check: needed for protected operations, good for five minutes, enforced twice". | **Not yet proven**: the request and approval functions for client tax IDs are not built. |
| 10 | **Exports were not logged.** | The 1099 export writes an audit entry every time it runs and refuses without recorded consent. | `supabase/tests/rls_isolation.sql` test: "every export that ran was written to the audit log" and test: "a refused export leaves no export entry". | Proven locally for the 1099 export. A general, recorded export of lists: **not yet proven** (not built). |
| 11 | **Weak change history**: seven fields only, values replaced by unsalted hashes that can be guessed and do not preserve the old value. | The audit log is written by database triggers on every sensitive table, with the old and new value of the changed fields. Contact details and document wording are redacted, not hashed. A network address is stored as a keyed hash that cannot be reversed without the key. | `supabase/tests/rls_isolation.sql` test: "the price change was recorded with the old and new value only", test: "contact details and payment references are redacted in the audit log" and test: "the audit entry carries a 64 character keyed hash, not the address". | Proven locally |
| 12 | **Deleting a client deleted its audit trail.** | The audit log has no link that removes entries with the record, and it refuses update, delete and truncate for everyone. | `supabase/migrations/0004_audit_log.sql`. `supabase/tests/rls_isolation.sql` test: "owner cannot delete from the audit log" and test: "the service role cannot empty the audit log". | Proven locally |
| 13 | **Staff could not be offboarded**: deleting an account was blocked by its records, or erased the hand-off history. | A member is disabled, not deleted. A disabled member reads nothing from that moment, and an owner can end their sessions. Their name stays on what they did. | `supabase/tests/rls_isolation.sql` test: "a disabled member reads nothing". `tests/server/auth.e2e.test.mjs` test: "an owner ends the sessions of a member". | Proven locally |
| 14 | **The last owner could demote themselves** and leave a company with no owner. | The database refuses. | `supabase/tests/rls_isolation.sql` test: "the last owner cannot demote themselves" and test: "the last owner cannot remove themselves". | Proven locally |
| 15 | **Real customer data in the code and in Git history** (about 200 customers in a migration). | Sample records are fictional by rule. A scan stops a pull request that contains a list of real-looking people, a provider export or a tax ID format. | `scripts/security/scan-pii.mjs`. `tests/security/scan-pii.test.mjs` test: "an import of real-looking customers in a migration is found (the NOVA case)". `.github/workflows/ci.yml`. The clean-up of the older repository: `docs/security/repository-cleaning.md`. | Proven here. The older repository is not cleaned yet. |

## A test of the tests

A test that cannot fail proves nothing. Two scripts break rules on purpose and expect the suites to notice:

* `supabase/tests/mutation_check.sh` loosens one database rule at a time and reruns the database tests.
* `tests/server/db.e2e.test.mjs` does the same for the server tables.

And in this folder's own tests, each check has its failing twin: `tests/security/check-headers.test.mjs` breaks one browser protection at a time, and `scripts/backup/restore-test.sh` changes one value and one rule after a restore to prove the comparison would catch it.

## What to do with a "not yet proven" row

It is an open item for the module that will build the feature. The rule for closing it: the feature ships with a negative test (the forbidden action is tried and refused), the test name is added to this page, and `node scripts/security/check-evidence.mjs` passes. A row is never moved to "proven" by editing this page alone.
